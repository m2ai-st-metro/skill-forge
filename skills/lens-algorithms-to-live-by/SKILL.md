# Lens: Algorithms to Live By

An evaluation LENS generated by `book-to-lens`. Apply it TO a target to surface what these
computer-science decision frames make you notice and value. It does NOT run a procedure and
has NO persona. Input: a named or pasted target (project / idea / pipeline / algorithm /
decision). Output: per-frame findings + verdict + what-to-change.

Source: the framework of "Algorithms to Live By" (Brian Christian & Tom Griffiths). Concepts
are applied as criteria, synthesized, not reproduced.

## How to run

1. Get the target. Ask the user to name or paste the project/idea/pipeline/decision to
   evaluate. If the target is a repo or pipeline, read enough of it to judge honestly (do
   not assert behavior you have not verified).
2. Walk each frame below against the target. For each: state the finding (**pass / flag /
   N/A**) and the specific evidence in the target. A frame that genuinely does not apply to
   this target gets **N/A** plus a one-line why (e.g. "Randomness/Sampling — N/A, a prose
   framework has no search space to sample"). N/A frames are excluded from scoring; do not
   manufacture a finding to fill a frame.
3. Score with the rubric (using the target-type-aware load-bearing set below).
4. Emit the "what to change" list, drawn only from flagged frames.
5. Emit the **routing block** (see "Follow-up routing" below): for each flagged frame, the
   concrete next step or downstream skill that acts on it. The lens judges; this is how the
   judgement stops being a dead end.

## The frames

1. **Optimal Stopping** — Is there an explicit "look, then leap" threshold, or is the target
   searching forever / snapping at the first option? Value: a stated stopping rule. Failure:
   open-ended deliberation, or committing before calibrating.
2. **Explore vs Exploit** — Given the remaining time horizon, is the explore/exploit balance
   right? Value: explore early, exploit late. Failure: exploring with no runway left, or
   exploiting a local optimum never pressure-tested.
3. **Caching (what to keep close)** — What deserves fast-access memory vs eviction? Value:
   keep by recency/frequency, evict deliberately. Failure: hoarding everything, or thrashing
   on cold misses.
4. **Scheduling (right metric)** — Is the target optimizing the right completion metric
   (minimize lateness? total time? weighted importance?)? Value: one chosen metric. Failure:
   busy-work ordering that optimizes nothing; context-switch thrash.
5. **Bayesian Priors** — What prior is the reasoning built on, and is it calibrated? With
   small data, is it over-reading noise? Failure: confident conclusions from a few data
   points; ignoring base rates.
6. **Overfitting** — Is the target optimizing to signal or noise? Is the plan more complex
   than the data justifies? Value: stop early, prefer simpler. Failure: endless tuning to
   past specifics that will not generalize.
7. **Relaxation** — Has an easier, constraint-relaxed version been solved first? Failure:
   stuck on the full hard problem with no simplified beachhead.
8. **Randomness / Sampling** — Would a sample or randomized approach beat exhaustive
   analysis here? Failure: brute-forcing a space a sample would answer.
9. **Backoff & Queue Depth** — On failure, does the target back off sanely vs hammer? Are
   queues / WIP too deep (buffer-bloat)? Failure: tight retry loops; unbounded backlogs that
   add latency, not throughput.
10. **Computational Kindness** — Does the target reduce downstream cognitive/operational
    load, or push the combinatorial work onto others? Failure: vague asks that make people
    or agents do the hard search.

## Scoring rubric

Load-bearing frames are **target-type-aware** — what matters most depends on what you are
judging. Pick the row that fits the target; default to the first if unsure:

| Target type | Load-bearing frames |
|-------------|---------------------|
| Default / mixed | 1 (stopping), 2 (explore/exploit), 4 (right-metric), 6 (overfitting) |
| Methodology / framework | 3 (caching), 4 (right-metric), 6 (overfitting), 10 (computational kindness) |
| Pipeline / system | 4 (right-metric), 6 (overfitting), 9 (backoff/queue), 10 (computational kindness) |
| One-shot decision | 1 (stopping), 2 (explore/exploit), 5 (Bayesian priors) |

State which row you used. A frame marked **N/A** cannot be load-bearing — if a load-bearing
frame is N/A for this target, note it and drop down to the next most relevant frame.

- **GREEN** — passes all load-bearing frames (for the chosen row) and most of the rest.
- **YELLOW** — one load-bearing frame violated (or several non-load-bearing frames).
- **RED** — two or more load-bearing frames violated.

State the verdict, then list what to change (one line per flagged frame, most impactful
first).

## Follow-up routing (turn flags into work)

The lens ends at insight unless each flag is routed to an action. After the verdict, emit a
short routing block — one line per flagged frame — mapping it to the concrete next step:

- **Fold into the artifact** — the flag names a missing piece of the thing under review; add it
  directly (the highest-value route when the target is a document/plan you control).
- **File as bounded work** — the flag is a real fix but out of scope now; capture it via
  `/quick` or `goal-maker` with owner/sink/kill so it is not lost.
- **Escalate / second opinion** — the flag is contested or high-stakes; route to
  `/gemini-rescue` or `/marks-plan`.
- **No action** — the flag is acknowledged but accepted; say so explicitly so silence is not
  mistaken for an oversight.

Two extra signals worth calling out when present: (a) if a SEPARATE review (e.g. `/gh-review`)
flagged the SAME weakness, note the corroboration — independent frames converging is a stronger
buy-signal than either alone; (b) do NOT propose scheduling this lens as a recurring loop on a
one-off target — a standing lens-audit with no owner/sink/kill is an orphan loop.

## What this lens is NOT

- Not a how-to for applying these algorithms (that would be a `book-to-skill` output).
- Not a persona of the authors (that would be a `book-to-persona` output).
- It judges a target; it does not build one.
